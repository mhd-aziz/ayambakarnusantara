# REVIEW — 5 Agustus 2026

Hasil audit menyeluruh kode (backend + frontend), dibaca bersama tiga sub-agent. Review ini murni baca kode, tidak ada file yang diubah saat proses berlangsung. Beberapa temuan awal dari sub-agent sudah saya cek ulang; yang tidak terbukti saya buang dari daftar ini.

Lingkup: backend 6.534 baris (32 file), SQL Supabase 713 baris, frontend 15.722 baris (75 file), plus tujuh dokumen acuan.

## Ringkasan

Project dalam kondisi sehat. Tidak ada bug yang bisa bikin aplikasi crash total. Yang perlu perhatian mayoritas soal order multi-toko dan beberapa penguatan keamanan di pinggiran. Detail di bawah.

## Backend

### Yang perlu diperbaiki

| Sev | Lokasi | Masalah |
|---|---|---|
| Tinggi | `productController.js` (buat + ubah produk) | Harga dan stok tidak punya batas atas. Seller bisa input angka raksasa yang merusak tampilan dan data |
| Tinggi | `orderController.js` (detail + update status seller) | Cek item pakai `.every()`. Order multi-toko ditolak padahal ada produk milik seller. Ini bagian dari keputusan desain order multi-toko (lihat ROADMAP #3) |
| Tinggi | `orderController.js` (`getSellerOrders`) | Ambil semua order lalu saring di Javascript. Lambat kalau order sudah banyak. Pakai index `shop_ids @> {shopId}` |
| Sedang | `ratingController.js` + SQL rating | SQL cek produk ada di order, tapi tidak memastikan order itu milik user yang mengirim. Bisa rating silang |
| Sedang | `chatController.js` | Teks pesan tanpa batas panjang, lokasi tanpa validasi rentang lat/long |
| Sedang | `multerConfig.js` | Cek tipe file hanya lewat MIME. File di-rename bisa lolos. Idealnya cek isi file (magic bytes) |
| Sedang | `storageHelper.js` | `extractPathFromPublicUrl` tidak menolak path berisi `..` |
| Sedang | `midtransConfig.js`, `chatbotController.js` | Secret key dan API key sempat ditulis ke log |
| Sedang | `paymentController.js` | Belum ada mekanisme refund dan riwayat perubahan status pembayaran |
| Rendah | `orderController.js` (seller orders) | Query customer satu per satu (N+1). Lambat kalau banyak seller |

### Yang sudah bagus

- State machine order ketat; transisi di luar daftar ditolak.
- RPC atomik di Postgres untuk buat/cancel order dan rating. Tidak ada race condition stok.
- Webhook Midtrans sudah benar: verifikasi signature sha512, idempoten, sinkronisasi status, notifikasi customer.
- RLS aktif di semua tabel. User hanya membaca datanya sendiri.
- Rating hanya bisa dari order selesai dan sekali per order + produk.
- Pembersihan saat hapus akun lengkap (file storage ikut dihapus).
- Tidak ada TODO/FIXME yang tertinggal di kode.

### Catatan temuan yang saya cek ulang

Beberapa klaim sub-agent tidak terbukti dan saya buang:

- "Kebocoran Google Maps API key (kritis)" tidak valid. Ada penjaga: kalau key tidak diisi, kode langsung menampilkan fallback dan tidak membuat URL berisi key.
- "Empat infinite dependency loop" tidak valid. `useCallback` memakai deps yang stabil, jadi tidak ada loop tak berujung. Yang ada hanya redundansi.
- "Bentuk respons notifikasi tidak konsisten" tidak valid. Backend dan frontend memang memakai `{ success, message, data[] }` dan konsisten.

### Yang sudah bagus

- Pesan chat dirender teks polos (fix XSS), tanpa `dangerouslySetInnerHTML`.
- `withCredentials` konsisten di hampir semua request yang butuh login.
- Ada fallback gambar offline, jadi tampilan tidak bergantung layanan luar.
- Semua operasi async punya state loading.
- Context pakai `useMemo`, tidak bikin render berlebihan.
- Form punya label dan tombol punya atribut aksesibilitas.

## Keputusan yang masih terbuka

1. Order multi-toko: blokir di checkout (cepat, kurang dari satu jam) atau sub-order per toko (redesain, dua sampai tiga hari). Ini menentukan tiga temuan tingkat tinggi sekaligus.
2. Mekanisme refund pembayaran online.
3. Batas atas harga dan stok produk.

## Prioritas yang saya sarankan

Kalau mau dikerjakan, urutan yang masuk akal:

1. Batas atas harga/stok di `productController.js`.
2. Putuskan order multi-toko (blokir atau sub-order), lalu rapikan `.every()`.
3. Kurangi insting secret key ditulis di log.
4. Validasi chat (panjang teks, rentang lokasi) dan rating (konsistensi order id).
5. Pakai index `shop_ids` untuk order seller.
